## API contract policy

The original architecture kit's `contracts/openapi.yaml` contained future endpoints that did not exist. In M0, this file is renamed **`openapi.future.yaml`**. A new `openapi.yaml` contains **only implemented M0 operations**. Runtime OpenAPI is generated by drf-spectacular and compared with the reviewed contract's (path, method) pairs. This is a minimal drift check; response-field compatibility assertions should be introduced with M1 and code-generated client DTOs.

## Security boundaries

- M0 only exposes anonymous liveness, readiness and build metadata routes. No upload or model integration exists.
- Django config enforces explicit production secrets, trusted hosts and secure cookies; deployment owners must still configure TLS, ingress, backups and monitoring.
- Worker-task execution is not exposed as an HTTP endpoint.
- Compose binds web/API ports to loopback; DB and Redis stay on the private Compose network.
- Request correlation IDs are created by the server rather than trusting arbitrary client-supplied IDs.
- Readiness reports only up/down state and never returns connection strings or exception details.

## Known limitations and next steps

1. **Rebrand runtime verification pending:** The original M0 Compose stack is running on the developer machine with healthy containers and successful Django, API readiness and Celery probes (user-reported, 2026-10-29). This authoring environment still lacks Docker and cannot reach npm/PyPI registries, so the renamed build requires fresh verification on the developer machine and in GitHub Actions. See `11_REBRANDING_MIGRATION.md`.
2. **Dependency integrity gate open:** Resolve dependencies in a networked environment; commit npm/Python transitive locks; use `npm ci` and hash/lock-enforced Python installs in CI and Docker. Suggested workflow: run `npm install --package-lock-only` in `apps/web`; run `pip-compile --generate-hashes -o requirements.lock requirements.txt` and an equivalent development lock command in `apps/api`; update Dockerfiles and CI to consume those exact files.
3. **No user authentication or dataset domain:** M1 creates real access-controlled projects/uploads. M0 is not a dataset tool demo.
4. **No observability stack:** M0 includes request IDs and health checks; centralized logs, metrics, tracing and alerting are later release tasks.
5. **No real external AI call:** Gemini is deliberately reserved for M3; only server-side adapter and privacy policy will authorize usage.
6. **Non-production Docker defaults:** Local credentials, optional hardening, resource limits and development Compose remain unsuitable for public internet deployment.
